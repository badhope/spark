# 核心能力差距矩阵（对标前沿 AI 编程应用）

> 2026-11-23。目的不是继续堆功能清单，而是先判断“核心模块能不能落地、能不能做出区隔”。外围小功能、冷门命令、猎奇交互不在本轮优先级内。

## 判断口径

一条能力算“核心”，必须同时满足：

1. 用户每天都会碰到，或缺了它就无法完成真实开发任务；
2. 竞品把它当作主路径，而不是彩蛋；
3. Spark 能通过自研、复用或 MCP/协议接入落地，不需要重新发明底层；
4. 落地后有可验证的验收标准（真实任务、时延、成本、失败恢复）。

按这个口径，核心能力收敛为 10 个模块，而不是几十个功能点。

## 前沿应用的共同基线

不逐家复刻产品，而是抽取 Cursor、Claude Code、Codex、opencode、Qoder/ZCode、Trae、Cline 这类产品已经在做的共同件。共性比单点功能更能说明“是不是同一代产品”。

| 共同件 | 前沿产品里的典型形态 | Spark 现状 | 结论 |
|---|---|---|---|
| 主入口 | 编辑器内 Agent、终端 Agent、桌面 App 三选一为主 | Web 工作台 + CLI/TUI + 桌面 + IDE + API，入口更多 | **入口数量够，深度不够** |
| 代码智能 | LSP/符号图、跨文件编辑、影响面、测试回灌 | LSP 9 工具、tree-sitter、语义索引、`apply_patch` | **单点有，系统性不足** |
| 长任务 | 计划、执行、验证、失败恢复、后台任务 | Goal、workflow DAG、检查点、队列；无人值守弱 | **有人监督可用，自动闭环不足** |
| 浏览器验证 | 开页面、点操作、看控制台/网络、截图、跑 E2E | Playwright Chromium 21 工具 | **能用，但只有单引擎** |
| 扩展生态 | MCP、插件、Skills、命令、市场 | MCP/ACP/A2A、Skills、命令、插件签名 | **协议面宽，目录太少** |
| 分发与协作 | 一键安装、自动更新、签名、分享、团队 | 安装脚本/EXE 路线、relay、远程接管；签名/公证缺 | **能装，交付链不完整** |

这张表回答“能不能实现前沿应用的能力”：**核心骨架能，完整产品力还不能。** 不能因为入口多、协议多，就宣称已经对标完成；也不能因为缺几个外围功能，就否定底层路线。

## 核心模块矩阵

| 模块 | Spark 当前 | 前沿应用基线 | 差距类型 | 优先级 | 路线 |
|---|---|---|---|---|---|
| **A. 浏览器能力层** | Playwright Chromium + 21 个 `browser_*`；侧栏实时画面；单浏览器实例 | 多引擎/多浏览器配置、已登录会话复用、扩展桥、远程浏览器、DevTools 性能/网络、下载上传、跨域 iframe、按域名授权 | 深度不足 + 生态未接 | **P0** | 自研抽象层 + 接 Playwright MCP / Chrome DevTools MCP / 浏览器扩展桥 |
| **B. Agent 长程执行** | ReAct loop、Goal 同流续跑、检查点、审批、队列、workflow DAG、子代理；Goal 跨重启需人工点继续 | 无人值守长任务、Goal 自动迭代验证、失败回滚、任务级预算、计划-执行-验收闭环、可恢复队列 | 部分可用，自动化深度不足 | **P0** | 先做“有人监督的闭环”，再放开无人值守；不先做花哨的 Team Canvas |
| **C. 代码智能与多文件编辑** | LSP 9 工具、tree-sitter 符号、语义索引、`apply_patch`、内联编辑、测试回灌 | 全仓库符号图、跨文件重构、依赖/调用链、编辑计划、影响面分析、自动修复测试 | 单点能力有，系统性不足 | **P0** | 接 Serena / Repomix / ast-grep；自有 LSP 做兜底，不重写语言服务器 |
| **D. MCP / 工具网关** | stdio/sse/streamable_http；registry 搜索、一键加入、工具命名空间、审批 | 大目录、OAuth、远程 MCP、工具级权限、健康检查、版本/撤销治理、市场 | 接入面窄、治理浅 | **P0** | 扩内置精选 + 远程 MCP + 工具网关；不自己造协议 |
| **E. 跨平台入口与分发** | Web、CLI/TUI、桌面壳、VS Code、JetBrains ACP、Neovim、移动布局、A2A | 一键安装、自动更新、签名/公证、崩溃恢复、系统集成、移动/远程连续 | 入口多，交付链不完整 | **P0** | 保留多入口；先做 Web/CLI 一键安装与自更新，再补签名/公证 |
| **F. IDE 原生体验** | VS Code 原生聊天/内联 diff；JetBrains/Neovim 走 ACP/External Tool；无 JetBrains 原生 inline UI | 编辑器内联补全、原生 diff、诊断/测试/调试联动、选区上下文、编辑器内 Agent | 有桥，缺原生深度 | **P1** | 先把 VS Code 做深；JetBrains 原生 UI 后置，不重复造 ACP |
| **G. 协作 / 分享 / 远程** | relay 单频道自托管、会话租约、手机壳、远程审批、device_admin | 多人共享、评论、任务分派、云端会话、组织权限、远程浏览器 | 单用户远程可用，多人未做 | **P1** | 先做“分享只读会话 + 远程接管”，不做账号体系与多租户 |
| **H. 观测 / 评测 / 成本** | OTel trace/metric/log、审计事件、成本台账、交付账本、30 任务矩阵 | 真实任务基准、回归门禁、trace 回放、成本预算、模型路由质量 | 有观测，缺产品级评测 | **P1** | 建“真实仓库任务集 + 延迟/成本/人工介入”三条标尺；不拿饱和矩阵当能力证明 |
| **I. 安全与隔离** | 审批档、工作区沙箱、保护路径、命令 token 检查、插件签名；Windows 仅 Job Object | 每平台强隔离、浏览器凭据隔离、网络策略、供应链扫描、提示注入防护 | Linux 可用，Windows/macOS 不完整 | **P1** | 先做“按平台如实降级 + 浏览器敏感站点阻断”；不伪造强隔离 |
| **J. 办公 / 知识 / 多模态** | 文档/会议/表格工作台、本地 OCR/转写、知识库 BM25+向量、截图/图片输入 | 多格式解析、版面理解、表格公式、长文档引用、跨文档检索 | 已有基础，格式覆盖不足 | **P2** | 接 MarkItDown / Docling / Unstructured；不自己训练 OCR |

## 核心能力的差异化怎么打

### 1. 浏览器不是“工具”，是“执行面”

多数竞品的浏览器能力是一个内置工具：开一个页面、点几下、截个图。Spark 的机会是把浏览器做成**能力层**：

- 浏览器配置（工作/个人/隔离）与已登录会话；
- 本地浏览器 + 远程浏览器 + 扩展桥三种接入；
- 页面、标签页、下载、上传、Cookie、控制台、网络、性能 trace 统一成工具；
- 按域名/动作授权，敏感站点默认阻断；
- 同一套浏览器能力在 Web、桌面、CLI、IDE 里都能调用。

这比“再做一个 browser_* 工具”更难被复制，也更符合“全平台、浏览器原生”的定位。

### 2. 开源不是“代码公开”，是“每一层都能换”

竞品的开源往往只开放客户端，模型、市场、云服务仍由厂商控制。Spark 的区隔是：

- provider 可换（OpenAI 兼容、国产模型、本地模型、fallback 链）；
- 工具可换（原生工具、MCP、插件）；
- 角色可换（`.claude/agents/*.md`、Skills、命令）；
- 界面可换（主题、Web 壳、桌面壳、移动布局）；
- 编排可换（YAML workflow、A2A、ACP）；
- 部署可换（单机、自托管、内网、relay）。

这不是“功能更多”，而是**控制权在用户手里**。对外要讲“可替换、可自托管、可审计”，不要讲成“本地优先”。

自定义程度要落到可验收的硬指标，而不是一句“高度可扩展”：

| 要换的东西 | 用户操作 | 不允许发生的事 |
|---|---|---|
| 模型 / 端点 | 设置页改 provider 或配置文件 | 改代码、重新打包 |
| 工具 | MCP 一键加入、插件安装 | 只能等官方发版 |
| 角色 / 工作流 | 放 `.claude/agents/*.md`、写 YAML | 被锁在厂商模板里 |
| 技能 / 命令 | 放 `.spark/skills/*.md`、`.spark/commands/*.md` | 必须上架审核才能用 |
| 界面 / 主题 | 换主题、换 Web/桌面壳 | 只能接受固定 UI |
| 部署 | 单机、自托管、内网 relay | 强制账号或厂商云 |

### 3. 协议广度是护城河，不是装饰

MCP 解决工具接入，ACP 解决编辑器接入，A2A 解决 Agent 间委派。三者同时可用，意味着 Spark 可以当“被其他 Agent 调用的执行端”，也可以当“调用其他 Agent 的编排端”。这比再做一个封闭插件市场更有长期价值。

## 先做什么，不做什么

### 第一轮核心落地拆解（建议 2–4 周）

| 工作包 | 范围 | 完成标准 | 不做什么 |
|---|---|---|---|
| CP-01 浏览器能力层 v1 | Playwright 引擎选择、profile 隔离、Chrome/Edge 扩展桥、远程浏览器配置 | 3 个真实站点任务可在 Chromium + Firefox/WebKit 至少各跑 1 个；敏感站点需二次确认 | 不接 Safari 原生扩展，不造浏览器引擎 |
| CP-02 MCP 工具网关 v1 | 内置精选 7→10、健康检查、工具 allowlist、失败降级、审计事件 | 每个 server 可一键加入/禁用；工具调用不绕过审批；冷启动 p95 有数据 | 不做公共插件市场上架审核 |
| CP-03 代码智能 v1 | Serena/Repomix/ast-grep 接入，LSP 兜底 | 3 个外部仓库完成“定位→改→测”闭环；跨文件影响面可读 | 不重写 LSP，不默认常驻大索引 |
| CP-04 长任务闭环 v1 | Goal 计划-执行-验收、失败回滚、队列预算 | 单任务可跨 20+ 回合，失败能回滚并续跑；人工介入次数可统计 | 不做无确认的全自动后台跑 |

### 先做（按顺序）

1. **浏览器能力层 v1**：Playwright MCP 接入、Chrome/Edge 扩展桥、已登录会话复用、远程浏览器配置；先把“能操作真实浏览器”做扎实。
2. **MCP 工具网关 v1**：内置精选从 3 个扩到 10 个左右，覆盖浏览器、代码检索、仓库打包、GitHub/GitLab、文档解析、安全扫描；统一权限、健康检查、按工具审批。
3. **代码智能 v1**：接 Serena（符号级检索/编辑）、Repomix（仓库打包/压缩）、ast-grep（结构化搜索）；自有 LSP 作为兜底。
4. **长任务闭环 v1**：Goal 计划-执行-验收、失败回滚、队列预算；先把“有人监督也能跑很久”做稳。
5. **跨平台交付 v1**：Web/CLI 一键安装、自更新、崩溃恢复；签名/公证按平台能力逐步补。

### 暂不做

- Team Canvas 式多专家可视化编排：先用 workflow + 声明式 agent 跑通，不先做产品壳。
- 自研浏览器引擎、自研 LSP、自研 OCR、自研向量数据库：已有成熟生态，重复造轮子没有收益。
- 冷门斜杠命令、猎奇主题、单点小工具：不进入核心路线。
- 完整 Tab 补全：先过真实模型接受率与 p95 延迟门禁，不先做。

## 验收标准

每个核心模块落地时必须带四条证据：

1. **真实任务**：至少 3 个外部仓库任务，不使用自家 fixture 自证。
2. **质量**：pass@1、人工介入次数、失败恢复成功率。
3. **时延/成本**：TTFT p50/p95、turn p95、单任务估算成本。
4. **安全**：越权、注入、凭据泄漏、恶意插件的负向测试。

没有这四条，只能标“初步可用”，不能标“对标完成”。
