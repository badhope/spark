# 行业调研与三项基准论证（2026-11-24）

> 范围：通用 AI 应用赛道、开源编程工具赛道；对象包括 Claude Code、GitHub Copilot、OpenAI Codex、Cursor、OpenCode、Cline、Aider、Continue、Qoder/ZCode 等公开产品与开源项目。
> 目的：为 Spark 的“前沿 AI 原生编程平台”定位提供可复核依据，不把宣传口径当结论。
> 现有逐项功能矩阵见 [`competitive-comparison.md`](competitive-comparison.md)，本文只回答三个基准问题。

## 0. 结论先行

1. **通用 AI 应用与编程 Agent 的边界不在“会不会写代码”，而在“能不能对代码变更负责”**：仓库上下文、可执行验证、diff 审批、测试回灌、回滚与审计，是编程场景的专属纵深。
2. **开源编程工具的优势是控制权与可组合，短板是长任务可靠性、交付链和治理**：OpenCode 的 client/server + LSP + 多 provider 很强，Cline 的逐动作审批很强，Aider 的 Git 原子提交很强，但“无人值守跑完真实任务”仍是共同缺口。
3. **AI 编程场景的潜能释放路径是“可验证的自动化”**：先把计划、执行、测试、修复、复验做成闭环，再把闭环接到队列、远程与团队治理；不是先堆聊天壳或功能清单。

## 1. 赛道一：通用 AI 应用

### 1.1 市场事实

- JetBrains 2026 开发者生态调查（15,000+ 专业开发者）：90% 的专业开发者在工作中至少每周使用 AI 编程 Agent，68% 每天使用。
- 同一调查的工作场所使用率：Claude Code 39%、GitHub Copilot 21%、OpenAI Codex 16%、Cursor 12%、OpenCode 7%。
- 采用速度远快于传统 IDE：Claude Code 从 2026 年 1 月的 18% 升到 5–7 月的 39%；Codex 从约 3% 升到 16%；Cursor 从 18% 降到 12%。
- 信任仍是条件性的：Stack Overflow 2026 受访者中，只有 6.6% 愿意把重要工作决策完全交给 AI 输出，76.5% 会先在本地运行 AI 产出再使用。

这些数字说明：**编程是通用 AI 最先规模化、也最容易被验证的落地场景**，但“生成得快”不等于“交付得稳”。

### 1.2 通用 AI 应用的能力边界

| 维度 | 通用 AI 应用 | 编程 Agent |
|---|---|---|
| 输入 | 自然语言、文件、图片、网页 | 自然语言 + 仓库 + 运行环境 + 测试 + 历史 |
| 上下文 | 对话上下文为主 | 跨文件符号、依赖、调用链、测试、Git 历史 |
| 输出 | 文本/图片/建议 | 可应用 diff、命令、测试结果、提交/回滚 |
| 正确性 | 依赖人工判断 | 可被编译器、测试、静态检查、运行时验证 |
| 风险 | 事实错误、版权、隐私 | 越权写盘、命令注入、凭据泄漏、破坏性变更 |
| 责任链 | 内容生产者 | 代码变更的审批、审计、回滚与交付 |

**边界结论**：通用 AI 应用可以“解释代码”，但只有编程 Agent 能“对代码变更负责”。Spark 不应该把自己做成通用聊天应用，也不应该把办公能力当主身份。

### 1.3 对 Spark 的直接要求

- 主路径必须是仓库任务：读代码→改代码→跑测试→修复→Review→回滚。
- 所有写操作必须可审计：谁批准、改了哪些文件、测试是否通过、能否回滚。
- 不以“模型多”“入口多”作为核心卖点；以“任务闭环可靠”作为卖点。
- 办公/文档/会议只能作为企业控制面的辅助能力，不能反向定义产品。

## 2. 赛道二：开源编程工具

### 2.1 代表项目的能力侧写

| 项目 | 架构优势 | 明显短板 | 对 Spark 的可复用点 |
|---|---|---|---|
| **OpenCode** | client/server；HTTP+SSE；TUI/桌面/Web/IDE 多客户端；LSP；75+ provider；六个内置 Agent；日志即队列，天然可恢复 | 系统提示词重；上下文管理不够优雅；无企业 SLA；无人值守交付链弱 | 服务端状态与多客户端模型；Agent 分工；LSP 诊断回灌；配置兼容 |
| **Cline** | VS Code 内逐动作审批；diff 可见；MCP 原生；checkpoint 回滚；浏览器/截图自检 | 高频审批拖慢长任务；强依赖 VS Code；跨平台入口弱 | 逐动作审批体验；checkpoint；视觉自检 |
| **Aider** | Git 原生；每次修改自动提交；tree-sitter 仓库地图；architect 模式 | 主要面向终端；编排与团队能力弱；无人值守能力有限 | 原子提交；仓库地图；提交信息规范 |
| **Continue** | 开源 IDE 扩展与 CLI；模型/上下文可插拔；企业自托管 | 长任务编排与执行面不如完整 Agent；工具生态相对窄 | 可插拔上下文；企业自托管 |
| **Claude Code** | 终端为主、强模型、5 层压缩、子 Agent、worktree 隔离、权限模式丰富 | 闭源；模型绑定较强；成本高；企业治理依赖 Anthropic | 压缩策略；权限分层；worktree 隔离 |
| **Codex CLI** | 终端/IDE/云；沙箱默认断网；审批策略清晰；云任务 | 本地执行面与开源生态弱；强绑定 OpenAI 账号/订阅 | 沙箱默认拒绝；审批双轴；云任务形态 |
| **Qoder / ZCode** | IDE/桌面/CLI/Web/手机多端；专家团队/动态工作流；国内模型与中文生态 | 闭源或重产品壳；团队编排成本高；可迁移性弱 | 多端形态；专家团队交互；中文模型适配 |

### 2.2 开源阵营的共同短板

1. **长任务可靠性不足**：多数工具有“循环”，没有“看门狗 + 无进展检测 + 失败回灌 + 可恢复状态”的完整运行器。
2. **交付链不完整**：安装、签名、公证、自动更新、崩溃恢复、团队权限经常缺一项。
3. **治理浅**：插件市场、工具权限、供应链签名、撤销列表、审计，很多项目只做到 manifest。
4. **上下文质量参差**：LSP、符号图、向量索引三者常只做一层；代码检索容易退化成 grep。
5. **评测自证**：功能矩阵很满，但真实仓库任务、人工介入次数、恢复成功率、成本数据很少公开。

### 2.3 开源阵营的优势

1. **控制权**：模型、工具、界面、部署可换；不被单一厂商锁定。
2. **可组合**：MCP/ACP/LSP/插件/Skills 让生态能力可以接进来，不必自研一切。
3. **可审计**：代码公开，权限、沙箱、日志可以做到企业可检查。
4. **成本弹性**：BYO 模型、本地模型、离线运行，适合预算敏感团队。
5. **社区扩散**：OpenCode 的 42% 认知度（awareness）说明，开源编程 Agent 已经进入主流开发者视野；其工作场景使用率仍只有 7%，差距正是交付链与可靠性的机会。

**矩阵结论**：Spark 不应复制某个单点功能，而应把“开源控制权”与“企业级交付责任”结合：可替换的每一层 + 可验证的每一条变更。

## 3. 三项基准论证

### 基准一：与通用 AI 应用的场景化边界

**结论**：Spark 的专属纵深是“代码变更责任链”，不是“更会聊天”。

必须落地的四项专属能力：

1. **仓库级上下文**：符号、依赖、调用链、测试、Git 历史，而不是只把文件塞进 prompt。
2. **可执行验证**：编译、测试、静态检查、浏览器 E2E；失败必须回灌到下一轮。
3. **变更治理**：diff 审批、沙箱、检查点、回滚、审计、成本。
4. **交付闭环**：分支、提交、PR、Review、发布；不是停在“建议代码”。

不该做的事：

- 不把文档/会议/表格当作主界面；
- 不用“模型数量/入口数量”替代任务成功率；
- 不做只会生成代码片段、不能验证的 Demo。

### 基准二：开源编程平台能力对标

**结论**：Spark 的相对优势应压在“闭环可靠性 + 审计 + 多入口共用后端”；相对短板必须如实承认。

| 能力 | Spark | 开源头部 | 判断 |
|---|---|---|---|
| 多入口共用后端 | Web/CLI/TUI/桌面/IDE/API/A2A | OpenCode client/server 强；Cline 偏 VS Code；Aider 偏终端 | Spark 入口更宽，但深度要补 |
| 逐动作审批 | 六档审批 + 规则 + 沙箱 | Cline 逐动作强；OpenCode 按 Agent 权限 | 已有基础，需把“无人值守”与“审批”解耦 |
| 长任务闭环 | Goal/Workflow/Queue 有，但无人值守弱 | 普遍缺完整运行器 | **最大机会点** |
| 代码智能 | LSP 9 工具 + tree-sitter + BM25/向量 | OpenCode LSP 强；Aider 仓库地图强 | 需要从“有”到“系统性” |
| 生态协议 | MCP/ACP/A2A 三协议 | OpenCode MCP/ACP；Goose MCP 参考实现 | 协议面宽，目录与治理不足 |
| 交付链 | 安装/更新/EXE 路线有；签名/公证缺 | 多数也缺签名/公证 | 谁先补齐谁先企业化 |
| 可审计 | 审批/沙箱/回滚/成本/OTel | 多数只有日志 | Spark 有差异化基础 |

### 基准三：AI 编程场景潜能释放路径

**结论**：潜能不在“让模型多写几行”，而在“让验证成本低于人工返工成本”。

可行路径：

1. **需求结构化**：把初始需求拆成可验收的任务、约束、测试入口与风险清单。
2. **计划可执行**：计划必须落到文件、命令、测试；不能只有自然语言步骤。
3. **执行有边界**：写操作走沙箱/审批/检查点；无人值守只放开工作区内安全动作。
4. **验证独立**：测试由运行器独立执行，不依赖模型自述“已完成”。
5. **失败回灌**：把 traceback、lint、类型错误、E2E 失败原样喂回下一轮。
6. **无进展熔断**：调用指纹、diff 指纹、测试指纹三路检测；重复无变化就停，不烧钱。
7. **可恢复**：每轮状态落盘；进程崩溃后从最后完成回合继续。
8. **成本可算**：单任务预算、token/费用上限、失败重试成本都入账。
9. **交付可审**：最终产出 diff、测试报告、风险清单、回滚点。

这九步就是 Spark 本轮 `autopilot` 的设计基线；任何“全自动”宣传必须能逐项对上。

## 4. 对 Spark 的差异化建设指令

### 4.1 独有创新点

1. **浏览器原生 + 编程执行面**：同一套 Agent 在 Web 工作台、浏览器工具、远程接管里运行；不是把浏览器当预览窗口。
2. **三协议可编排**：MCP 接工具、ACP 接编辑器、A2A 接其他 Agent；Spark 既能被调用，也能调用别人。
3. **审计型自动化**：无人值守不是“关掉审批”，而是把审批策略、沙箱、检查点、成本、测试证据绑定到同一条运行链。
4. **开源可替换**：模型、工具、角色、界面、工作流、部署全部可换；控制权在用户手里。
5. **失败回灌闭环**：测试失败不是错误提示，而是下一轮输入；这是编程 Agent 与聊天应用的分水岭。

### 4.2 不允许的走偏

- 把办公工作流写成产品主身份；
- 用“功能数量”替代“真实任务成功率”；
- 用概念 Demo 冒充全自动；
- 把第三方子智能体当施工队，绕过本项目的架构与验收；
- 把“已排期”写成“已交付”。
